# Energine Simple — установка

Выпуск новой визитки по шагам (шаблоны страниц, свои цвета, проверка) — `docs/NEW-SITE.md`.

Состояние: **этап 7 — чистое ядро**. Остаются модули share, user и seo, в базе 21 таблица: дерево
разделов и текстовые страницы, пользователи, группы и права, переводы, регистрация и кабинет, файловый
репозиторий, шаблоны писем, карта сайта. Модуль apps (новости, обратная связь), галерея и вложения разделов,
мёртвый код ядра, CodeMirror и свой календарь вырезаны на этапе 7, остальное — на этапах 1–6 (см. README).
Визуальный редактор — Jodit (в формах и при правке на странице), файлы загружаются через `fetch`, поля
даты — встроенные поля браузера. Формы защищены токеном против подделки запросов, вход — лимитом попыток,
пароль восстанавливается по одноразовой ссылке; почта — через `mail()` или SMTP; тема — своя, без
фреймворков. Сайт ставится одной командой установщика в пустую базу. Спецификации:
`docs/superpowers/specs/2026-09-26-energine-simple-design.md` (этапы 1–6) и
`docs/superpowers/specs/2026-10-01-energine-simple-stage7-core-design.md` (этап 7).

Площадка: `simple.energine.org` (ISPConfig, `web97`), база `c1senergine`.

## Раскладка на ISPConfig

Document root ISPConfig фиксирован (`web/`), а `open_basedir` пускает PHP только в `web/`,
`private/` и `tmp/`. Поэтому код лежит в `private/`, а в `web/` — только точка входа.

| Путь (от `/var/www/clients/client1/webNN`) | Что это |
|---|---|
| `web/index.php`, `bootstrap.php`, `auth.php`, `resizer/` | точка входа, копии из `htdocs/` репозитория; после обновления кода копируются заново |
| `web/uploads/` | файлы площадки (в git только каркас `htdocs/uploads`) |
| `web/system.config.php` | симлинк на `private/energine/configs/system.config.<домен>.php` |
| `web/images`, `scripts`, `stylesheets`, `templates` | генерирует `setup linker`, руками не править |
| `private/energine/` | репозиторий: ядро `core/`, сайт `site/`, `setup/`, `sql/`, `tests/`, `docs/` |
| `private/energine/configs/system.config.<домен>.php` | конфиг площадки с паролем базы, режим 600, вне git |
| `private/energine/tests/local.php` | учётные данные тестов, режим 600, вне git |

Ядро и проект — одно дерево: `ROOT_DIR` указывает на корень репозитория, модули лежат
в `core/modules` без симлинков. `setup linker` их не трогает (`tests/setup-linker.sh`).

Всё принадлежит `webNN:client1`: в vhost стоит `disable_symlinks if_not_owner`, nginx
отдаёт файл по симлинку, только если у ссылки и цели один владелец. Команды приложения
запускаются от владельца: `runuser -u webNN -- …`. Git — от root, после него
`chown -R webNN:client1 private web`.

Конфиги веб-сервера не трогаются. Нужны две переадресации — их задают в ISPConfig в поле
nginx-директив сайта:
- адресов без файла — на `index.php` (`try_files $uri $uri/ @rewrites` → `rewrite ^ /index.php last`);
- адресов превью — на ресайзер:
  `rewrite "^/resizer/w([0-9]+)\-h([0-9]+)/(.*)$" /resizer/timthumb.php?w=$1&h=$2&src=$3&zc=2;`.
  Имя `timthumb.php` осталось от прежнего ресайзера, чтобы правило не менялось; внутри — свой ресайзер на GD
  (`ImageResizer`, раздел «Картинки»).

## Развёртывание

Команды для `simple.energine.org`. Для другой площадки поменяйте `web97`, домен и базу.

```sh
H=/var/www/clients/client1/web97
R=$H/private/energine
```

1. **Репозиторий** и хук, который не пускает пароли в коммиты. Git работает от root,
   а после `chown` репозиторий принадлежит владельцу площадки, поэтому root должен ему
   доверять:
   ```sh
   git clone <адрес репозитория> $R
   git -C $R config core.hooksPath .githooks
   git config --global --add safe.directory $R
   ```
2. **Точка входа:**
   ```sh
   cp $R/htdocs/index.php $R/htdocs/bootstrap.php $R/htdocs/auth.php $H/web/
   cp -a $R/htdocs/resizer $H/web/
   cp -a $R/htdocs/uploads $H/web/
   ```
3. **Зависимости:**
   ```sh
   cd $R && runuser -u web97 -- env HOME=$H/tmp COMPOSER_HOME=$H/.composer php8.5 /usr/bin/composer install --no-dev
   chown -R web97:client1 $H/private $H/web
   ```
4. **Установка** — одна команда в пустую базу (база и её пользователь заводятся в ISPConfig):
   ```sh
   cd $H/web && runuser -u web97 -- php8.5 index.php setup install --domain=simple.energine.org \
     --db-name=c1senergine --db-user=c1newenergine --admin-email=admin@example.org
   ```
   Установщик:
   - проверяет расширения PHP (pdo_mysql, dom, xsl, simplexml, mbstring, gd, openssl, fileinfo);
   - пишет конфиг площадки из шаблона `configs/system.config.default.php` —
     `configs/system.config.<домен>.php`, режим 600, и ссылку на него `web/system.config.php`;
     отладка в нём выключена (`site.debug` = 0: с ней посетитель видел бы пути сервера на странице
     ошибки), стенду разработки её включают вручную;
     если конфиг уже есть (например, заполнен вручную), берёт базу и адрес сайта из него, тогда
     нужен только `--admin-email`;
   - до первого изменения базы проверяет параметры, e-mail и пароли, соединение и то, что база
     пуста: в непустую базу установка не ставится;
   - ставит схему и базовые данные (`sql/structure.sql`, `sql/data.sql`): языки, служебные
     страницы и админку, группы и права, переводы, почтовые шаблоны;
   - создаёт администратора (`--admin-email`, `--admin-name`, по умолчанию `Admin`) в группе
     с полным доступом;
   - адрес сайта пишет только в конфиг: `site.domain` — хост из `--domain` или `--url`, с портом, если он
     нестандартный (`--url=http://127.0.0.1:8123/` → `127.0.0.1:8123`), `site.root` — путь из `--url`
     (по умолчанию `/`); в базу адрес не пишется;
   - раскладывает статику (`setup linker`).

   Пароли в аргументах не принимаются — их видно в списке процессов и в истории команд. Без
   переменных окружения установщик спросит пароль базы и пароль администратора с терминала
   без эха. В сценариях — переменные `ENERGINE_DB_PASSWORD` и `ENERGINE_ADMIN_PASSWORD`
   (например, из файла с режимом 600). Ошибка — код выхода 1 и причина; если установка
   прервалась на середине, база заполнена частично: её нужно очистить и запустить установку
   снова. Параметры базы: `--db-host`, `--db-port` или `--db-socket` (сокет сервера базы, тогда
   хост и порт не нужны). `--config=ФАЙЛ` — конфиг в другом месте, `--no-static` — без статики.
5. **Демо-контент** (для `simple.energine.org`; в установку не входит):
   ```sh
   cd $H/web && runuser -u web97 -- php8.5 index.php setup demo
   ```
   Разделы и тексты («Информация», «Возможности» и их подстраницы), демо-посетители
   (`sql/demo.sql`) и файл репозитория (`sql/demo/uploads` → `web/uploads`). Ставится только на свежую
   установку.
6. **Тесты:** `tests/local.php` (образец — `tests/local.php.example`, режим 600, вне git) —
   e-mail и пароль администратора, локальный почтовый ящик для писем тестов.

Установку заново — снять всю базу, поставить установщиком и демо, с новым случайным паролем
администратора в `tests/local.php` — делает `tests/tools/rebuild.sh --yes-drop-everything`.
Сверить установку с нуля с базой площадки, не трогая её, — `tests/tools/fresh-check.sh`,
проверить сам установщик — `tests/tools/install-check.sh` (временный экземпляр MariaDB).

### Обновление

Статика в `web/` (`images`, `scripts`, `stylesheets`, `templates`) — ссылки на файлы модулей в
репозитории, при любом режиме отладки: после `git pull` их содержимое уже новое. Если файлы статики
добавились, удалились или переименовались, а также после правки `htdocs/*.php`:
```sh
cp $R/htdocs/index.php $R/htdocs/bootstrap.php $R/htdocs/auth.php $H/web/
cp $R/htdocs/resizer/timthumb.php $H/web/resizer/
rm -f $H/web/resizer/timthumb-config.php   # конфиг прежнего timthumb (до этапа 5 надёжности)
chown -R web97:client1 $H/private $H/web
cd $H/web && runuser -u web97 -- php8.5 index.php setup linker
```
Новый скрипт модуля (например, окно истории текста `TextBlockHistory.js`) попадает в import map страниц только
после `setup linker`, и файл должен принадлежать владельцу площадки — чужой файл веб-сервер отдаёт как 404.
Изменения базы между версиями — переходные скрипты `sql/cut/stage*.sql` (см. ниже).

Модули ядра перечислены в `modules` конфига площадки. Если модуль убран из ядра (этап 7 убрал `apps`), его
строку из конфига нужно удалить до `setup linker`: с модулем без каталога `setup linker` отказывается, не трогая
статику, и называет модуль.

### Переход базы полной системы на форк

Сайт, работающий на полной системе Energine, переходит на форк без переустановки: к его базе по
порядку применяются `sql/cut/stage1.sql` … `stage7.sql` — каждый рассчитан на базу предыдущего этапа. Скрипты убирают таблицы, колонки и переводы вырезанного,
добавляют новое; тексты сайта не трогают. Страницы со своим XML в старой раскладке (меню и
вход в колонке, контейнер `mainMenuContainer`) сбрасываются на шаблон страницы — `stage5.sql`
перечисляет их в выводе клиента `mysql`, их раскладку при необходимости собрать заново в
админке. `stage6.sql` (мультисайт) ставится только на базу с одним сайтом и одним корнем дерева
разделов — иначе отказ до любых изменений с объяснением; он удаляет таблицы доменов и привязки групп
к сайтам, номер сайта у страниц и флажки сайта, а страницу редактора сайтов превращает в «Настройки
сайта» (`admin/settings/`). Адрес сайта после него берётся из конфига — перед переходом проверьте
`site.domain` и `site.root`; адреса из удаляемой таблицы доменов скрипт печатает, другие имена сайта
после перехода переадресуются на адрес из конфига. `stage7.sql` (ядро) удаляет таблицы новостей, обратной
связи и вложений разделов, разделы их админки, письма обратной связи и их переводы; разделы на шаблонах
новостей, обратной связи и галереи и разделы со своим XML с этими компонентами становятся текстовыми
страницами (тексты остаются) — скрипт перечисляет их номера в выводе, их страницы стоит проверить. Свой XML
разделов с другими удалёнными компонентами (галерея, вложения, выбор раздела, мёртвый код) сбрасывается так же.
После перехода из `modules` конфига площадки удаляется строка модуля `apps` (см. «Обновление»).
`stage10.sql` и `stage11.sql` добавляют константы (общий текст ошибки, образцы секций и названия шаблонов
страниц); `stage11-demo.sql` — только для демо simple.energine.org (главная — «Лендинг», страницы «Услуга» и
«Контакты»), на рабочие сайты не ставится.
Проверка — `tests/tools/migration-check.sh`.

## Адрес сайта и «Настройки сайта»

Одна установка — один сайт. Адрес сайта задаёт конфиг площадки: `site.domain` — хост, с портом, если он
нестандартный (`127.0.0.1:8123`), и `site.root` — путь сайта (`/`). Схема (http или https) берётся из
запроса, хост — никогда: поддельный заголовок `Host` не меняет ни ссылок, ни писем, ни редиректов.
Страница, открытая по другому имени или порту (`www`, IP, чужой `Host`), переадресуется (301) на ту же
страницу по адресу из конфига: формы работают только там, где их `Origin` совпадает с адресом сайта.
Cookie сайта ставятся на `.хост`, для адреса с портом, IP и `localhost` — только этому хосту.

Название сайта, ключевые слова и описание страниц по умолчанию (по языкам), запрет индексации
(`NOINDEX` закрывает `robots.txt` и `google-sitemap`) и дополнительные параметры сайта правятся
в админке — «Настройки сайта» (`admin/settings/`, кнопка на панели страницы). Добавить или удалить
сайт нельзя.

На `simple.energine.org` в `web/` лежит статический `robots.txt` панели ISPConfig (`User-agent: *`):
nginx отдаёт его вместо страницы `robots.txt` сайта, и запрет индексации из настроек до `/robots.txt`
не доходит. Страница сайта заработает, когда этот файл удалят.

## Тема

Разметка сайта — `site/modules/main/transformers/energine.xslt` (шапка, меню, язык, вход, содержимое, боковая
колонка, подвал, формы сайта) и компоненты `ui.xslt` (кнопка, сообщение, поле формы, ширина страницы). Оформление —
утилиты Tailwind CSS v4 прямо в классах разметки; повторяющиеся элементы — именованные шаблоны `ui.xslt`, а не
строки утилит в каждом шаблоне.

**Стили собираются**, собранный `site/modules/main/stylesheets/main.css` лежит в git — сайту сборка не нужна:
```sh
bash tools/get-tailwind.sh                          # бинарник Tailwind 4.3.3 (без Node), сумма сверяется
cd $H/web && runuser -u web97 -- php8.5 index.php setup css
```
Исходник — `tailwind.css` рядом с `main.css`:
- `@theme` — переменные дизайна (цвета bg, fg, muted, border, primary, danger, ok; радиус ui; ширина страницы);
  их значения — переменные светлой и тёмной схем. Перекрасить сайт — поменять переменные схем;
- `@custom-variant` — свои варианты для вложенных элементов (`fields:`, `labels:`, `blocks:` …): «&» в классе XSLT
  пишется как `&amp;`, и такие классы сканер Tailwind не собирает (`tests/css-build.sh` это запрещает);
- база темы — элементы текста из редактора и классы ядра, общие с админкой. Сброс Tailwind (preflight)
  не подключается: админка на страницах сайта опирается на стили браузера.

После правки XSLT или `tailwind.css` — `setup css`, иначе `tests/css-build.sh` (в регрессии) упадёт.

**Админка** — второй вход той же сборки: `core/modules/share/stylesheets/admin.tailwind.css` → `admin.css`
(тоже в git, `setup css` собирает оба файла). Грузится только администратору и в окнах; гостю не нужна.
- утилиты админки — с префиксом `a:` (`a:flex`, `a:px-3`): так они не совпадают ни с утилитами сайта (у
  администратора на странице оба файла), ни с классами ядра, на которые опирается JS (`grid`, `hidden`, `block`);
  `css-build.sh` проверяет, что утилит без префикса в `admin.css` нет;
- переменные дизайна админки — в её `@theme` (`--a-color-*`), тёмной схемы у админки нет;
- то, что пишет не один шаблон или переключает JS (каркас `e-pane`, вкладки, поля форм, строки грида, панели,
  дерево), — правила слоя `admin` под классами ядра;
- порядок слоёв в обоих файлах один — `theme, base, components, admin, utilities`: какой файл подключится первым,
  тот задаёт порядок;
- значки — спрайт `core/modules/share/images/icons.svg` (около 20 контурных значков 24×24): в XSLT — шаблон
  `admin-icon` (`icons.xslt`), в JS — `Energine.icon(имя)`; у кнопки панели в конфиге — `icon="add"`. Font Awesome
  и картинки кнопок удалены.

Правила темы сайта не касаются контейнеров админки (`.e-pane`, панели администратора, рамки окна). Страница ошибки вне раскладки сайта —
`core/modules/share/transformers/error_page.xslt`.

В `web/` стили попадают ссылками (`setup linker`). nginx площадки отдаёт файл по ссылке, только
если у ссылки и файла один владелец (`disable_symlinks if_not_owner`): файл темы, записанный от
root, отдаётся с кодом 404 — после правки `chown web97:client1`.

## Шаблоны страниц и секции

Визитка собирается из готовых шаблонов страниц — их выбирают в редакторе структуры при создании или правке
раздела:
- «Лендинг» (`main/landing.content.xml`): первый экран, услуги, отзывы, призыв к действию, контакты;
- «Услуга» (`main/service.content.xml`): первый экран, описание (обычный текст страницы), цены, вопросы, призыв;
- «Контакты» (`main/contacts.content.xml`): заголовок и текст страницы, контакты.

Файлы — `site/modules/main/templates/content/`, в `web/templates/content/main/` они попадают через `setup linker`.

**Секция** — контейнер шаблона с атрибутом `section` и текстовым блоком внутри; владелец правит её текст на
странице. Вывод — `site/modules/main/transformers/sections.xslt`, вид — правила `.ui-section-*` в `tailwind.css`.
Пустая секция гостю не выводится, администратору показывает образец текста (константа `TXT_SECTION_SAMPLE_*`).
```xml
<container name="cta" section="cta">
    <component name="section_cta" class="TextBlock">
        <params><param name="section">cta</param></params>
    </component>
</container>
```
`class` — короткое имя компонента (ищется в модулях сайта, затем ядра; полное имя тоже работает). `section` задаёт
номер текстового блока и образец секции: hero 11, services 12, prices 13, reviews 14, gallery 15, faq 16,
contacts 17, cta 18 (номера не меняются — по ним в базе лежат тексты). Разметка текста владельца, она же образец:

| Секция | Текст | Вид |
|---|---|---|
| `hero` | `h1`, абзац, ссылка, картинка (необязательно) | картинка — фон с затемнением, ссылка — кнопка |
| `services` | `h2`, список: в пункте `strong` и описание | пункты — карточки сеткой |
| `prices` | `h2`, список тарифов: `h3`, цена абзацем, вложенный список, ссылка | тарифы колонками, ссылка — кнопка |
| `reviews` | `h2`, цитаты `blockquote` с `p` и `cite` | цитаты карточками |
| `gallery` | `h2`, картинки | сетка картинок 4:3 |
| `faq` | `h2`, пары `h3` + абзац (или `details`) | вопросы с разделителями |
| `contacts` | `h2`, абзацы с адресом, ссылки `tel:`, `mailto:`, на карту | колонками на широком экране |
| `cta` | `h2`, ссылка | полоса основного цвета, ссылка — кнопка |

Формы обратной связи и вложений страницы в Energine Simple нет: контакты — ссылками, галерея — картинками
из текста.

## Конфиги компонентов

Состояния компонента (адреса, поля, панели кнопок) — `*.component.xml` в `config/` модуля или сайта. Конфиг может
хранить только отличия от другого: `<configuration extends="DivisionEditor.component.xml">` — состояния базового
(базовый ищется рядом с файлом, затем как обычный конфиг — файл проекта, сайт, модуль компонента, — затем в модулях
ядра; сам файл пропускается, поэтому конфиг сайта с именем конфига ядра наследует ядро), одноимённые заменяются на месте, новые добавляются в конец,
`<state name="…" remove="1"/>` убирает состояние. Порядок — как у базового: от него зависят веса шаблонов адресов.
Цепочка из нескольких конфигов допустима, цикл — ошибка разработчика. Так устроены `SiteDivisionEditor` и
`FileRepositorySelect`.

Тип поля в конфиге (`<field type="…">`) — одно из значений `FieldType` (`string`, `text`, `integer`, `boolean`,
`select`, `file`, `htmlblock`, `hidden` …, те же строки, что константы `FieldDescription::FIELD_TYPE_*`); опечатка —
ошибка разработчика `ERR_DEV_UNKNOWN_FIELD_TYPE` с именем поля, а не странное поле в форме (`tests/field-type.php`
проверяет все конфиги). Описание колонок таблиц ядро читает из `information_schema` — три запроса на процесс, кэша
схемы на диске нет (файловый кэш ядра включается ключом `site.cache` и каталогом `cache/`, в шаблоне конфига его нет),
поэтому после изменения таблиц ничего сбрасывать не нужно.

## Ошибки и отладка

- Любая ошибка PHP (в том числе `TypeError`) — страница ошибки ядра: вне отладки посетитель видит общий текст,
  подробности уходят в журнал PHP; `display_errors` включается только при `site.debug`. У JSON-запросов админки
  ошибки 403/404 — ответ `{"result": false, "errors": […]}`.
- `?debug` (XML документа) и `?struct` (XML структуры страницы) работают только при `site.debug`. На рабочем сайте
  отладка выключена. В XML документа при отладке — `document/@queries` (число запросов к базе за страницу) и список
  `<queries><query>…`: видно, что лишнего не читается; бюджет держит `tests/queries.php`.
- Заполнители адресов компонентов типизированы: `[int]` — число или список чисел через запятую; `[pid]`,
  `[pageNumber]`, `[fromId]`, `[toId]`, `[smap_id]` — одно число; `[sortDir]` — `asc|desc`, `[sortField]`, `[direction]` — идентификатор,
  `[token]` — буквы, цифры, `_`, `-`. Адрес с другим значением — 404.
- `resizer/` не загружает картинки с чужих адресов и не показывает ошибок: на всё, кроме картинки из `uploads/`,
  отвечает пустым 404 (раздел «Картинки»).

## Адреса страниц

- У страницы один адрес — со слешем на конце: `/about` отвечает 301 на `/about/` (вместе с именем хоста из
  `site.domain` — одной переадресацией). Без слеша остаются «файлы» (точка в последнем сегменте: `robots.txt`,
  картинки), запросы JSON админки и POST.
- Старые адреса не ломаются: когда в форме раздела меняют сегмент адреса или родителя, прежний путь страницы и её
  подразделов записывается в `share_sitemap_aliases`, и запрос старого адреса получает 301 на нынешний — с языком,
  хвостом пути (`page-2/`, подраздел) и строкой запроса. Псевдоним указывает на страницу, а не на путь, поэтому
  цепочек нет; страница, снова созданная по старому адресу, важнее псевдонима; удаление страницы уносит её старые
  адреса. Страница, которую посетитель открыть не может (нет права, выключена на его языке), переадресацией не
  выдаётся — 404. Существующей базе таблицу добавляет `sql/cut/stage17.sql`.

## Картинки

Превью и картинки в текстах (`/resizer/wШИРИНА-hВЫСОТА/путь`) уменьшает свой ресайзер на GD (`ImageResizer`; точка
входа — `web/resizer/timthumb.php`, имя задано правилом веб-сервера). Вид — как у прежнего timthumb: картинка вписана
в размер по центру с полями (у JPEG и GIF — белые, у PNG и WebP — прозрачные), нулевая сторона — по пропорции, не
больше 1500×1500. Только обычные файлы картинок (JPEG, PNG, GIF, WebP) внутри `web/uploads/`; остальное — пустой 404.
Готовые картинки — в кэше `<upload_tmp_dir>/energine-resizer/` (на ISPConfig — `webNN/tmp/energine-resizer/`): его
можно очистить в любой момент, записи старше 30 дней удаляются сами; замена файла даёт новую картинку (ключ кэша —
время и размер файла). Браузер получает ETag и `max-age` 10 дней, повторный запрос — 304. Нужен PHP GD с JPEG, PNG и
WebP — это проверяет `setup check`.

## Удаление страниц

Страница с подстраницами не удаляется — сначала подстраницы (иначе каскад снёс бы поддерево с текстами). Служебные
страницы (сегменты корня `admin`, `login`, `register`, `restore-password`, `profile`, `sitemap`, `google-sitemap`,
`robots.txt` и всё внутри них) не удаляются. Если на страницу ссылаются тексты других страниц, редактор структуры
спрашивает второй раз и показывает эти страницы. Очистка текста на одном языке не трогает другие языки. В репозитории файлов нельзя удалить
папку вместе с её содержимым одним выделением (строка «..» в выделении — отказ); несколько файлов удаляются целиком —
записи и файлы.

## Почта

По умолчанию письма сайта уходят через `mail()` — sendmail сервера. Чтобы отправлять их через
SMTP-сервер, в конфиг площадки добавляется блок `mail.smtp` (пример — в
`configs/system.config.default.php`):
- `host`, `port`;
- `from` блока `mail` может быть и с именем («Сайт <noreply@example.org>»): в конверт SMTP идут
  только адреса;
- `encryption`: `tls` (или `starttls`) — STARTTLS (порт 587 или 25; если сервер его не
  предлагает, письмо не уходит), `ssl` — TLS сразу (порт 465), пусто — без шифрования; регистр
  не важен, другое значение (опечатка) — письмо не уходит, причина — в журнале ошибок PHP;
- `username`, `password` — вход AUTH PLAIN или LOGIN; без шифрования пароль идёт открытым
  текстом, это годится только для локального сервера;
- `cafile` — свой центр сертификации, если сертификат сервера выпущен не общедоступным;
- `timeout`.

Сертификат сервера проверяется по имени хоста. Если письмо не ушло, причина пишется в журнал
ошибок PHP. Клиент свой (`core/modules/share/gears/SmtpTransport.php`), сторонних библиотек нет.

## Проверка

```sh
bash $R/tests/setup-linker.sh      # linker не трогает модули в core/modules
bash $R/tests/no-traces.sh         # нет следов вырезанного (этапы 1–7) и MooTools (этап 8)
bash $R/tests/regression.sh        # все сценарные наборы и журнал ошибок PHP
bash $R/tools/get-phpstan.sh       # PHPStan (phar, сумма сверяется) — один раз, в git не попадает
bash $R/tests/phpstan.sh           # PHP: ошибки сверх базовой линии phpstan-baseline.neon
bash $R/tests/jscheck.sh           # JS: типы без сборки (tsc --noEmit по JSDoc, нужен Node)
cd $H/web && runuser -u web97 -- php8.5 index.php setup check    # перед сдачей: отладка, адрес, демо, robots, названия, ссылки, переводы
cd $H/web && runuser -u web97 -- php8.5 index.php setup manual --out=$H/private/OWNER-$(date +%F).md  # памятка владельцу
bash $R/tests/tools/install-check.sh   # установщик на временном экземпляре MariaDB
bash $R/tests/tools/fresh-check.sh     # установка с нуля и демо == база площадки
```

**Статический анализ.** PHPStan уровня 2 (`phpstan.neon`) и `tsc --noEmit` по JSDoc (`jsconfig.json`) входят в
регрессию: новая ошибка — провал. Известные ошибки PHP записаны в `phpstan-baseline.neon` (11 записей: методы конкретных
билдеров через `getBuilder()`, `Switcher::setState` через `getControlById()`, `BreadCrumbs::addCrumb` через
`getBlockByName()`); исправили одну — обновите линию из корня репозитория:
`php8.5 tools/phpstan.phar analyse --generate-baseline`. Сайту ни PHPStan, ни Node не нужны — это инструменты
разработчика; на машине без них наборы пропускаются только явно: `PHPSTAN_SKIP=1`, `JSCHECK_SKIP=1`.

**Сдача владельцу.** `setup check` — проверка перед сдачей, строки `OK`/`WARN`/`FAIL`, код выхода 1 при `FAIL`,
базу не меняет: отладка выключена, адрес сайта задан, нет демо-пользователей и статического `web/robots.txt`, у
включённых страниц есть названия на открытых языках (пустые тексты — предупреждение), битых ссылок и непереведённых
констант нет; предупреждения — языки «в подготовке», NOINDEX у обычных страниц, почта без SMTP. `setup manual`
печатает памятку владельцу (`docs/OWNER.md` с адресами площадки и списком языков; `--out=ФАЙЛ` пишет файл — не в
`web/`). Язык можно готовить скрыто от посетителей: «Языки» → снять «Открыт посетителям» (виден только редакторам).

Обход браузером и подробности по тестам — в `tests/README.md`.

## Секреты

- Пароль базы хранится только в `configs/system.config.<домен>.php`.
- Пароль администратора для тестов хранится только в `tests/local.php`.
- Оба файла вне git. Хук `.githooks/pre-commit` отклоняет коммит, в котором оказался любой
  из этих паролей: он проверяет индекс через `.githooks/secret-scan.php`.
- Хук подключается на каждом клоне отдельно: `git config core.hooksPath .githooks`.
- `git clean -fdx` и `git stash --all` в рабочем дереве площадки удалят или спрячут конфиг
  площадки и `tests/local.php`: они лежат внутри репозитория, но вне git. Не запускайте их
  в `$R`.

## Особенности simple.energine.org

- **Страницы ошибок.** В ISPConfig у сайта должен быть выключен пункт «Own Error-Documents»
  (на simple.energine.org выключен 2026-10-04): иначе nginx подменяет ответы Energine с кодами
  4xx/5xx статичными страницами из `web/error/` (`ERROR 404 - Not Found!`). Отказ по токену формы
  по-прежнему отвечает кодом 422 — на хостинге с включённой подменой посетитель и так увидит,
  что форму нужно отправить ещё раз.
- **Администратор.** Пароль администратора задаётся при установке; для тестов он хранится
  только в `tests/local.php`.
