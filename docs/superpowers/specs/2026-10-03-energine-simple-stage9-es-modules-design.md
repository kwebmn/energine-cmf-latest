# Energine Simple, этап 9 — ES-модули вместо ScriptLoader и карты зависимостей

Дата: 2026-10-03. Продолжение этапа 8 (переход с MooTools на чистый JavaScript закончен, площадка на 588eb598).
Владелец выбрал подход: нативные ES-модули и import map, без сборщика.

## 1. Цель

Сейчас зависимости скриптов объявляются вызовом `ScriptLoader.load('A', 'B')` в начале файла; `setup scriptMap`
читает эти вызовы и пишет карту `web/system.jsmap.php`; `Document.php` по карте выстраивает классические
`<script src>` в нужном порядке, а классы видят друг друга как глобальные переменные (`var Form = class Form …`).

После этапа:
- **29 скриптов ядра** (`core/modules/share/scripts`, `core/modules/user/scripts`) — ES-модули: зависимости — их
  собственные `import`, классы — `export`; порядок загрузки и поиск зависимостей делает браузер.
- **Import map** в каждой странице (`<script type="importmap">`): имя модуля → адрес с версией (`?v=` — время
  изменения файла). Кэш браузера обновляется у каждого изменённого файла, в том числе у зависимостей, которые
  страница подключает не сама.
- `ScriptLoader`, `web/system.jsmap.php`, `setup scriptMap` и разрешение зависимостей в `Document.php` уходят.
- Сборщика нет: выкладка прежняя — код в живое дерево, `setup linker` (шаг `setup scriptMap` больше не нужен).

## 2. Как устроено

### 2.1. Модули
- Файл — модуль: `export class Form …` (именованные экспорты), зависимости — по имени из import map:
  `import {Toolbar} from 'Toolbar';`. Имя модуля — путь файла от `web/scripts` без `.js` (`Form`, `GridManager`,
  `jodit/jodit.min`), как в нынешней карте.
- `Energine.js` — `export const Energine = {…}`; `ScriptLoader` уходит. Модуль, который пользуется `Energine`,
  импортирует его (сейчас он доступен всем как глобальный).
- Вложенные классы остаются свойствами экспортированных (`Toolbar.Button`, `TreeView.Node`, `Form.RichEditor`,
  `FileRepository.Grid`); у файлов с несколькими классами экспортируется то, что нужно другим (`Grid` и `GridManager`,
  `Filters`, `PathList` и т. д.).
- **Jodit** — сторонний UMD-файл: `EnergineEditor` подключает его импортом без имён (`import 'jodit/jodit.min';`),
  Jodit, как и сейчас, кладёт `Jodit` в `window` (он сам пишет в `self`).
- **Глобальные имена — только договор страницы**, явно, в одном месте у каждого: `window.Energine` (для
  встроенных скриптов шаблонов сайта и отладки), `window.ModalBox` (окна ищут общую очередь окон в `window.top`),
  экземпляры поведений по id компонента (на них ссылаются `onclick` в шаблонах полей и раздела),
  `componentToolbars`, `document.FileRepository`, `window.ScrollBarWidth`. Классы глобально не видны.

### 2.2. Страница
- `Document.php` вместо `javascript/library` (цепочки зависимостей по карте) отдаёт **список модулей для import map**:
  все `.js` в `web/scripts` (ссылки ядра и Jodit) с версией `filemtime` — около 30 проверок файла на запрос, как
  сейчас для версий библиотек; поведения страницы (`javascript/behavior`) — как сейчас.
- `document.xslt`:
  - `<script type="importmap">` — первым из скриптов страницы (до любого модуля);
  - настройка `Energine` (адреса, язык, токен, режим) — `<script type="module">`, импортирует `Energine`;
  - запуск поведений — `<script type="module">`: импорт классов поведений этой страницы (по одному на имя), затем,
    как сейчас, обработчик `DOMContentLoaded` создаёт панель страницы и поведения; экземпляры поведений —
    `window[id]`;
  - `javascript/variable` — как сейчас (классический скрипт, модулей не касается).
- Встроенные скрипты шаблонов — модули: переводы (`document.xslt`, `list.xslt`, `divisionEditor.xslt`) импортируют
  `Energine`; панели гридов и форм (`toolbar.xslt`, `file.xslt`) — `Toolbar`. Модули выполняются по порядку после
  разбора страницы и до `DOMContentLoaded`, поэтому порядок «настройка → переводы → запуск поведений → привязка
  панелей» остаётся прежним.
- `onclick` в шаблонах полей (`openFileLib`, `openQuickUpload`, `clearFileField`) и раздела
  (`resetPageContentTemplate`) — без изменений: экземпляры поведений глобальны.

### 2.3. Установка и выкладка
- `Setup`: действие `scriptMap` и его разбор `ScriptLoader.load` удаляются; `setup linker` удаляет устаревший
  `web/system.jsmap.php`, если он есть.
- `tests/tools/install-check.sh`, `tests/tools/tempdb.sh`, `docs/INSTALL.md` — без `setup scriptMap`.

### 2.4. Что не входит
Сборка, минификация, TypeScript; перевод `onclick` в шаблонах на обработчики; шаблоны сайта (`site/`) — встроенных
скриптов там нет; серверная часть.

## 3. Проверки

Пишутся до переделки и проходят на нынешнем коде, кроме отмеченных:
- **Import map** (`public`, гостем и администратором): у страниц есть import map; у каждого адреса в нём — `?v=`;
  все скрипты ядра загружаются модулями (тип запроса `script`, адрес из import map) — **красные до переделки**.
- **Нет `ScriptLoader` и глобальных классов**: `window.ScriptLoader`, `window.Form`, `window.GridManager`,
  `window.Toolbar` не определены, `window.Energine` и `window.ModalBox` — определены — **красная до переделки**.
- **Версия меняется с файлом** (стенд): после изменения времени файла скрипта его адрес в import map другой.
- **Все модули импортируют то, чем пользуются** (`no-traces`, новая категория `modules`): в скриптах ядра нет
  `ScriptLoader`; каждый, кроме Jodit, — модуль (`export`); каждый класс ядра, упомянутый в чужом модуле,
  импортирован им (проверка по именам экспортов) — **красная до переделки**.
- Проверки этапа 8, которые создают объекты классов в странице (`new TreeView.Node`, `new Toolbar.Button`,
  `Form.toQueryString` и т. п.), берут классы через `import()` в странице, если их нет в `window` — проходят и до,
  и после.
- Регрессия, аудиты `public`, `grids`, `editors`, `theme`, `crawl` (все страницы и окна без ошибок JS) — на стенде;
  после выкладки — на площадке.

## 4. Порядок работ
1. Проверки (новые; проверки этапа 8 — через `import()` там, где берут классы).
2. Модули: `Energine` и 28 скриптов (`import`/`export`, договор глобальных имён), `Document.php` (список модулей),
   `document.xslt` и встроенные скрипты шаблонов — одним переходом: модуль не может опереться на глобальный класс
   классического скрипта и наоборот.
3. `Setup` без `scriptMap`, устаревшая карта удаляется, инструменты тестов и документы.
4. Документы, итоговая проверка, ревью ветки.
5. Выкладка и проверка на площадке (точка отката; код от имени web97; `setup linker`; при провале — откат: прежний
   код и `setup linker && setup scriptMap`).

## 5. Риски
- **Пропущенный импорт** — `ReferenceError` только на пути, где имя используется. Защита — проверка `modules` в
  `no-traces` (все имена классов ядра в чужих модулях импортированы), аудиты и `crawl`.
- **Браузеры без import map** (Safari до 16.4, Chrome до 89, Firefox до 108 — до 2023 года): скрипты страницы не
  запустятся. Формы сайта (вход, регистрация, профиль) отправляются и без скриптов, проверка на сервере остаётся;
  админка рассчитана на актуальные браузеры. Полифил не добавляется (внешние адреса запрещены, свой — лишняя
  сущность).
- **Модули выполняются после разбора страницы:** встроенный классический скрипт, который сразу обращается к
  `Energine` или классу, сломается — поэтому все такие скрипты шаблонов становятся модулями (раздел 2.2); проверка —
  `crawl`.
- **Окна:** общая очередь окон — `window.top.ModalBox`; модуль `ModalBox` в каждом окне берёт её у верхнего окна и
  сам кладёт себя в `window` — как сейчас.

## 6. Результат
Скрипты ядра — ES-модули с явными `import`/`export`; страницы подключают их через import map с версиями файлов;
`ScriptLoader`, карта зависимостей и `setup scriptMap` удалены; сборщика нет.
